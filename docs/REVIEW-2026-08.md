## 1. Verdict

If a scholarship panel member, Imperial admissions reader, DFI recruiter, or infrastructure investor opened this tomorrow, I think the likely conclusion would be: **there is a serious practitioner behind this, the underlying publishing system is unusually considered, but the public site still presents itself like an ambitious project in construction rather than a finished body of authoritative work.** The reading shell, route discipline, accessibility work, draft safety, editor recovery, and security controls are stronger than the homepage suggests. The public credibility layer is weaker than the system underneath it. A first-time reader gets a deliberately informal hero with almost no subject or identity context, an About page that omits the professional record that actually earns trust, and a curriculum whose scale is made visible mainly through a large number of “Coming soon” items. That is not the conclusion you want. The site should make a serious reader think “this person has a point of view and evidence of competence; the curriculum is a structured roadmap behind the published work.” Today it is too easy to think “large planned syllabus, still mostly unbuilt.”

## 2. Top 5

### 1. Reframe the unwritten curriculum as a roadmap, not as inventory

This beats everything else because the gap between planned and published work is the single largest credibility signal on the site, and the current implementation deliberately amplifies it. Anonymous readers can expand modules and see every draft title, deck, “Coming soon” label, and author byline. The August 3 gate record says this exposes titles and decks for **159 unwritten essays**. `docs/SESSION_LOG.md:24-58`; `src/pages/FinanceTrackIndex.tsx:45-165`.

Keep the 49-module architecture. Do not pretend it is finished. But make the published corpus the primary object and the full curriculum a secondary, explicitly labelled roadmap. I reject the alternative of deleting the curriculum or reducing it to the five published essays because the structure itself is useful evidence of how you think. The problem is not ambition. The problem is presenting planned output in the same visual grammar as authored output.

### 2. Build the missing credibility surface on About

The About page currently contains a one-line subject statement, Selected Essays, and a reading stack. It does not tell an admissions reader what you do, what you have done, why you are qualified to write about finance/accounting/transition topics, or where the boundary sits between personal views and current employment. `src/pages/About.tsx:92-176`. The footer is currently the only place that gives your full name and contact links. `src/components/Footer.tsx:8-32`.

This beats a sixth-place print fix because a panel needs to know who wrote the argument before it cares how elegantly the PDF prints.

### 3. Make the backup real, not merely coded

The daily backup workflow exists and is correctly designed to fail rather than create a false sense of safety, but the latest session handoff still says the two secrets must be set and the first run turned green. `docs/SESSION_LOG.md:18-22`; `.github/workflows/backup.yml:1-43`. Essay bodies do not regenerate from migrations. Until there is a successful artifact and a tested restore path, the authored corpus still has a single operational point of failure.

This is the only Top 5 item that can destroy the work rather than merely weaken how people perceive it.

### 4. Make the hero pass the ten-second credibility test

Current source says: “Let’s get insanely, damn good at numbers.” It then says numbers should drive everything and tell us the past and probability of the future. It does not say finance, accounting, project finance, development finance, Indonesia, climate transition, or who the author is. `src/components/HeroSection.tsx:35-80`.

The line has voice. It also makes the panel spend the first screen decoding what the site is. For a general creator site that is tolerable. For an admissions/employer credibility instrument it is a tax. I would retain personality, but add one precise scope sentence or change the opening register. The exact voice choice belongs to the owner; the purpose-fit defect does not.

### 5. Turn publishing into a complete distribution event

The repo has a thoughtful build-time prerenderer for published essay OG metadata, but it only refreshes on a deployment. A CMS publication or metadata edit does not itself regenerate the raw HTML. The script also uses the global `/og-image.png` whenever an essay has no thumbnail, skips page-level accounting canonicals, and there is no `sitemap.xml` or RSS file in `public/`. `scripts/prerender.mjs:1-70,120-220`; `index.html:10-27`; `public/robots.txt:1-18`.

The sixth item is print/PDF. Print matters for panels, but distribution comes first: a reader must receive and open the right card before print quality can matter.

## 6. Questions for me

These are owner decisions. The code should not decide them by momentum.

### Q1. How visible should the unfinished curriculum be?

**Recommendation:** keep all 49 modules publicly discoverable, but make the default experience published-first and put all unwritten titles behind an explicit roadmap control. This preserves ambition and honesty without making 159 missing essays the dominant visual fact.

**Trade-off:** full immediate visibility proves the curriculum is specific, not hand-wavy, but it also makes delivery progress look tiny. Hiding every planned title makes the site look fuller but throws away useful structure. The middle position is stronger.

### Q2. Does “Let’s get insanely, damn good at numbers” stay as the H1?

**Recommendation:** keep the personality but reduce the burden on that line by adding explicit field scope immediately below it. If you want the lowest-risk admissions/employer version, soften “damn”.

**Trade-off:** the current line is recognisable and human. It is also high-variance with a conservative panel. The site does not need to sound like a bank annual report, but the first screen has less room for ambiguity than an essay body.

### Q3. Does IELTS remain in the global primary navigation?

**Recommendation:** keep the IELTS material public, but move it under a secondary Resources/Learning surface rather than keeping it co-equal with Finance, Development Finance and Green Transition in the main professional navigation.

**Trade-off:** public IELTS material demonstrates learning discipline and can help readers. In primary chrome, it also makes the site look partly like a study-prep portal exactly when you want a scholarship panel to treat the rest as professional intellectual work.

### Q4. Does “The Next Big Thing” keep its name?

**Recommendation:** retain the editorial section if you use it, but add an outsider-legible descriptor or rename it around its actual categories: technology, economy, society, environment and governance.

**Trade-off:** the current label has voice but communicates no thesis. A descriptive label gives up some personality and gains immediate legibility.

### Q5. What exactly should the About biography disclose?

**Recommendation:** current professional function, a compact prior-experience line, exact CFA status, core writing domains, LinkedIn/email, and nothing about the scholarship applications themselves. Add one sentence that views are personal.

**Trade-off:** too little context wastes genuine credibility. Too much turns the page into a résumé or looks like it was built for assessors. The target is enough evidence to establish authority, then back to the work.

### Q6. Should every planned essay carry an author byline?

**Recommendation:** no. Put authorship at page/section level for the roadmap and keep row-level bylines for published work.

**Trade-off:** repeated bylines make ownership explicit but add no information after the first row and visually reinforce the number of unfinished items.

### Q7. Do you want publishing to trigger deployment automatically?

**Recommendation:** yes. Mint a Vercel Deploy Hook and connect it server-side to published-content changes. Do not expose the hook URL in browser code.

**Trade-off:** automatic rebuilds cost build minutes and need debouncing if you edit metadata repeatedly. The alternative is a manual deployment ritual that guarantees stale previews eventually.
