## 2. `fsre_published`: why the read fails, and the order that fixes it

```
$ VITE_SUPABASE_URL=… VITE_SUPABASE_PUBLISHABLE_KEY=… npx vite-node scripts/world/check-published.ts
check-published: published models answered 406
$ curl … -H "Accept-Profile: fsre_published" "$URL/rest/v1/model_packages?select=package"
{"code":"PGRST106","hint":"Only the following schemas are exposed: public, graphql_public","message":"Invalid schema: fsre_published"}
```

The cause is one step earlier than gate 0 thought: **the schema does not exist** in
`asypkbkiebjvvpimewfp` (schemas present: `auth, extensions, graphql, graphql_public, public,
realtime, storage, supabase_migrations, vault`; no `fsre`, no `fsre_published`). Its DDL lives in
FSRE (`dikagustiana/fsre-skills`, `db/postgres/0000`–`0004`), which creates the `fsre_*` roles
(passwords set out of band), the `fsre` tables, the approval functions and the views, and already
grants the read: `0003_published.sql` gives `anon` `USAGE` on the schema and `SELECT` on its views,
`0004_live.sql` gives `anon` `SELECT` on `fsre_published.model_packages`. There was nothing to
grant on, so no SQL was run, and the schema was not exposed: **exposing a schema that does not
exist breaks the whole Data API** (PostgREST cannot build its schema cache, PGRST002), the essays
included.

In this order:

1. Apply FSRE's migrations to the site's project as FSRE's `06_DEPLOYMENT` describes:
   `0000_bootstrap_roles.sql` as `postgres`, set the role passwords, then `0001`, `0002`, `0003`,
   `0004a`, `0004` as `fsre_owner`.
2. Check the read grant (it should already be there; the two grants are idempotent and read-only):
   ```sql
   select has_schema_privilege('anon', 'fsre_published', 'USAGE')                    as usage,
          has_table_privilege('anon', 'fsre_published.model_packages', 'SELECT')      as can_read,
          has_table_privilege('anon', 'fsre_published.model_packages', 'INSERT')      as can_write;
   -- expect true, true, false. If not:
   grant usage on schema fsre_published to anon;
   grant select on fsre_published.model_packages to anon;
   ```
3. Expose it. Dashboard: https://supabase.com/dashboard/project/asypkbkiebjvvpimewfp/settings/api
   → **Data API** → **Exposed schemas** → add `fsre_published` next to `public` and
   `graphql_public` → **Save**. Or the Management API with a personal access token
   (https://supabase.com/dashboard/account/tokens):
   ```
   curl -X PATCH "https://api.supabase.com/v1/projects/asypkbkiebjvvpimewfp/postgrest" \
     -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" -H "Content-Type: application/json" \
     -d '{"db_schema": "public, graphql_public, fsre_published"}'
   ```
4. Verify: `npx vite-node scripts/world/check-published.ts` → `HTTP 200, N package(s)` (0 until a
   package is approved through `fsre.approve_package`).

## 3. Backups, then the migration

| Workflow | Secret | Required | What it is |
|---|---|---|---|
| `backup.yml` (Content backup) | `VITE_SUPABASE_URL` | yes | the project URL |
| | `SUPABASE_SERVICE_ROLE_KEY` | yes | service-role key (an anon dump would skip the drafts; the script refuses) |
| `db-backup.yml` (Full database backup) | `SUPABASE_DB_URL` | yes | session-pooler connection string as `postgres` (Project Settings → Database → Connection string → Session pooler) |
| | `BACKUP_PASSPHRASE` | no | encrypts the artifact with gpg AES256; without it the dump uploads unencrypted |

Not set as of the scheduled runs today: Content backup run 37864361350 (2026-10-09 00:21Z) failed
with `FATAL: VITE_SUPABASE_URL not set` and both variables empty; Full database backup run
37865673456 (00:36Z) failed with `SUPABASE_DB_URL is not set. No backup was taken.` and uploaded no
artifact. Neither has ever succeeded (68 and 4 runs). Starting them from this session was refused
(`workflow_dispatch`: 403 "Resource not accessible by integration"). The organisation is on the
free plan, so Supabase keeps no backups of its own and has no branching.

So **`20261008120000_essay_world_tags.sql` is applied nowhere**, not even rehearsed. Once a run of
each workflow is green with its artifact:

1. Rehearse on a local Postgres (Supabase branching needs a paid plan): restore the
   `db-backup` artifact into `supabase start` (the restore order is at the top of
   `db-backup.yml`), apply the file, then
   `select column_name from information_schema.columns where table_name='essays' and column_name like 'world_%';`
   → four rows, and the essays row count unchanged.
2. Apply to production through `apply_migration` with the same name, so the migration history
